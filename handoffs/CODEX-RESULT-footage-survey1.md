## 1. Geometry inputs and output classification

**Current seam:** `computePricing()` calls `getStats()` directly (`index.html:4275`) and `calcAutoMaterials()` directly (`index.html:4291`); the latter calls `getStats()` again and iterates S.elements for both fence runs and gates (`index.html:2041`, `index.html:2047`, `index.html:2209`). A replacement stats object alone is insufficient. Actual fence element discriminator is **`type:'fence'`**, not `type:'run'`; `runId` supplies identity (`index.html:3374`). Gate elements carry start/end, gateType, runId, fenceType and specs; posts carry pos, auto, runId, fenceType and runSpecs (`index.html:3366`, `index.html:915`, `index.html:1890`).

G = measured/detected from geometry or stored geometric elements today; C = arithmetic from explicit counts/LF/specs once supplied. G→C indicates a geometric measurement whose downstream arithmetic needs no coordinates.

| Every getStats output / row field | Classification and source |

| byRunId.sections, sectionFt | G→C: complement of gate intervals along each run (`index.html:849`, `index.html:1966`). These cut lengths are distinct from total net LF. Gate edges snap to endpoints within tolerance; tiny fabric gaps ≤ tolerance disappear from sections, while net LF subtracts raw openings. Thus sum(sectionFt) can differ slightly from netFt. |
| cornerSet, cornerPosts, terminalPosts | G: `buildCornerSet` tests nearby run endpoint pairs and angle change >0.15 radians (`index.html:1870`); corner threshold 18 world px (`index.html:718`). getStats uses rounded point keys and suppresses endpoints on gate posts (`index.html:1972`); sets represent physical endpoints, not counts per incident run. | byRunId.termCt, cornerCt | G→C: physical endpoint purchased once, assigned to first claiming run in S.elements order (`index.html:1977`). Mixed-spec/type joins can change material allocation if order changes. |

Pure spec/table dependencies: height, postHeightIn, role embed and valid diameter, rail/face-board/truss flags, add-ons, strand count/arm, type/style, FOOTING bag weight/schedule. `hydrateRunSpecs` clones existing fields; it does **not** derive a complete resolved spec from height alone (`index.html:786`). Height handler derives defaults separately (`applyHeightDrivenSpecs`, `index.html:1408`); role-depth lookup and bags at `index.html:1376`.

Slope: getStats uses 2D endpoint distance, no elevation; no slope multiplier in material takeoff. grade/slopePercent are stored/displayed specs. UI grade change toggles job-wide slope checkbox (`index.html:3908`), while computePricing charges slope per **gross job LF** (`index.html:4369`); setting a typed grade alone would not emulate that UI side effect. Per-foot labor uses net LF; demo uses gross LF; hours override replaces LF and gate labor (`index.html:4340`). Crew×days and equipment are not existing first-class labor/equipment models.

## 2. Minimum inputs per footage line

“Same BOM” requires the same resolved takeoff, not merely one LF total. Fields below are conceptual requirements, not a chosen schema.

- Stable line identity/order and segmentation: fenceType and resolved per-line specs; preserve which quoted line becomes which drawn run(s). Splitting/merging runs can alter per-run ceilings, sleeves, shared-post allocation and sectionQty (§1).
- Explicit **gross vs net** LF convention. Existing run gross includes gate openings; typed net must be expanded to gross with nonoverlapping opening widths to match demo/slope/allocation. LF by type alone loses per-run rounding information (§1 gross/net rows).
- Fabric sections/cut lengths, or enough gate positions along each run to derive them: gate type, actual width, offset from run start, owner line, overlap/adjacency/end placement. Width+count alone cannot recover post spacing or pack/panel rounding (§1 section/gate rows).
- Topology/end roles: each endpoint free/end, corner, shared collinear or gate; shared endpoint identities/adjacency and owning line/spec assignment. Keep physical terminal/corner/gate post purchases separate from fabric terminal/corner/gate-end counts. “Two corners” does not identify which lines share them (§1 role/count rows).
- Post-spacing rule and actual line-post count: auto enabled/disabled, per-line spacing, and any manual/stored-post exceptions. Normal freshly generated count per positive section is max(0,ceil(sectionLF/spacing)−1); exact floating thresholds follow autoPostsForRun, without unitsPerSection's epsilon. Existing saved jobs may not match this derived count (§1 lineCt row).
- Resolved specs: height; post overall length; per-role diameter/embed and relevant legacy aliases; rail/truss/face-board switches; add-ons; barb strands/arm. Full serialization also retains dirty/default flags to avoid later changes re-deriving different values (§1 material families; `index.html:1335`, `index.html:1408`).
- Shared job pricing context (not per-line geometry): same COST_DB including units/packs, LABOR, MARKUP, FOOTING, job site flags, hours override, manual lines and draft/frozen-quote status. Owner-run gate allocation must remain for per-type section totals (`index.html:4302`, `index.html:4337`, `index.html:4393`). Equipment could be represented by separately priced manual material rows today, but then uses material markup/cost grouping, not a distinct equipment category (`index.html:4284`). Crew×days requires defined crew/day/hour-rate semantics; multiplying today's crewHourlyRate by crew size is not established by source.

Counts sufficient to price a particular ordinary yard are not sufficient to invent its actual foreman layout. If only LF/type/height/ends/corners/gate widths are initially known, gate positions, cut lengths and exact post counts remain assumptions or later inputs; equality cannot be guaranteed for arbitrary layouts.

## 4. Equality example — three 50-ft sides, interior 4-ft walk gate
